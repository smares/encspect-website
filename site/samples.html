Samples Wanted

Encspect recognizes an encoder from what the encoder leaves in a file. It can only learn that from files whose origin is known. If you have such files, you can help.

Why samples matter

Every encoder leaves traces: version strings, header layouts, padding bytes, habits in how it lays out frames, gapless-playback data. Encspect reads these and reports what they say about the encoder and the software that wrote the file.

A detection rule is only added when it can be checked against a file that the encoder really wrote. A guess from a description of an encoder is not enough, and a file whose origin nobody remembers cannot teach anything. So the most valuable file is one where you know exactly what made it.

What makes a sample useful

  • The encoder, its version and its settings are known. A program name and version number, plus the bitrate mode, quality setting or preset you chose. "Unknown" is a fine answer for a part you cannot recall; say so rather than guess.
  • The file is as the encoder wrote it. No re-saving in an editor, no tag editing, no trimming, normalizing or converting afterward. Any of these can overwrite the very traces Encspect looks for.
  • Short is fine. Ten to thirty seconds, or a file under a few megabytes, is plenty. A short file encoded directly is better than a long one cut afterward.
  • Several settings from one program are welcome. The same encoder at different bitrates, modes or channel counts shows which traces change and which stay.

The kinds of files wanted

A specific encoder and version

Files from a program whose exact version you know. Examples: a particular release of a command-line encoder, a music player's built-in ripper or converter, an audio editor's export.

Old and rare encoders

Programs from the 1990s and 2000s, discontinued tools, early versions, patched or tuned builds, and the encoders inside hardware players, recorders and phones.

Unusual settings

Uncommon bitrate modes, very low or very high bitrates, odd sample rates, mono and multichannel files, joint stereo switched off, and options that change how a file is laid out.

Unusual containers and wrappers

Audio in a container it is not usually found in, such as Matroska, Ogg, MP4 or WAV carrying a codec you would not expect, or files written by a muxer or tagging tool with its own habits.

Damaged files

Truncated downloads, files cut mid-frame, files with bad checksums or garbage at the end. Say what happened to the file, and keep an undamaged copy if you have one.

Anything that Encspect gets wrong

A file where Encspect names the wrong encoder, names none although you know which one it was, or reports a finding that looks mistaken.

What not to send

  • Music you do not have the right to share. Commercial recordings are not needed. Encode a clip of your own, a recording you made, or a test tone or noise instead; the encoder's traces are the same.
  • Files with personal data in their tags. Names, e-mail addresses, account or license IDs and comments can all end up in tags. Remove them or blank them with characters of the same length, and say that you did. Better still, start from a file with no tags.
  • The encoder program itself. Send files and what is known about them, not installers or program files.

How to share

  1. Put the file on any file host that gives you a download link.
  2. Open a sample issue on GitHub: its form asks for the link and for what is known about the file.
  3. Write what you know about how it was made: the program and version, the operating system, the settings you chose, whether it added tags by itself, and anything odd that happened.
  4. Say how the file may be used: only for checking Encspect, or also as a test file in the public project, released under CC0 (no rights reserved), so that anyone may use it. If you are not sure, say that; nothing is published without your consent.

Offer a sample

Unsure whether a file is useful? Describe it in an issue anyway; a description of what you have is a good start. Opening an issue needs a free GitHub account.
